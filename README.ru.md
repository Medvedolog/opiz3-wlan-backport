# Orange Pi Zero 3, Zero 2W и Zero 2: встроенный Wi-Fi (AW859A / UWE5622) на OpenWrt 25.12

**[English version](README.md)**

На Orange Pi Zero 3 стоит модуль AW859A (UNISOC UWE5622, SDIO). В основном
ядре Linux драйвера для него нет, OpenWrt его не поддерживает. Этот
репозиторий нацелен на доведения встроенного WiFi до полноценного WLAN OpenWrt на **официальном
OpenWrt 25.12.5**: 2,4 и 5 ГГц, точка доступа и клиент, настройка через
LuCI/UCI, как у любого другого радио.

Чем проект отличается от прежних сборок:

- **Официальное ядро OpenWrt.** Образ собран официальным ImageBuilder,
  поэтому любой kmod с downloads.openwrt.org ставится через `apk`. Драйвер и
  несколько пакетов, которых нет в OpenWrt, берутся из нашего подписанного
  apk-репозитория.
- **Драйвер исправлен, а не просто собран.** Драйвер производителя защищён
  от найденных падений (30 патчей, 010–330). Он показывает только реально
  измеренные значения и не принимает настройки, на которых падает прошивка.
- **Прошивка разобрана.** Прошивку Wi-Fi разобрали настолько, чтобы
  объяснить её сбои. Все результаты опубликованы в [docs/](docs/).

> Статус: **beta 2** ([релиз](../../releases/tag/opiz3-25.12.5-beta2)).
> Проверено на Zero 3: точка на 5 ГГц VHT80 и 2,4 ГГц, клиент на 2,4 ГГц,
> LTE как аплинк, трафик и TX-скорость по клиентам, восстановление
> прошивки, Ethernet после горячей перезагрузки. Zero 2W: загружается, точка
> работает (отчёт пользователя). Экспериментально: точка и клиент
> одновременно (репитер). Недоступно: уровень сигнала клиентов (прошивка его
> не отдаёт). Zero 2: не проверен. Подробнее — в разделе [Статус](#статус);
> установка и обновление — в [описании beta 2](docs/releases/opiz3-25.12.5-beta2.md).

## Статус

Результаты на железе (Zero 3): таблица ниже — от 2026-10-06 (образ r15 с
исправлениями r16/r17), плюс проверка перед выпуском beta 2 от 2026-10-11
(первая загрузка, Ethernet и точка после трёх `reboot`, передёргивания
питания и `sysupgrade`). Команды — в [docs/TEST-PLAN.md](docs/TEST-PLAN.md):

| Что | Состояние |
|---|---|
| Запуск SDIO, загрузка прошивки | Работает (SDIO 50 МГц, 4 бита; прошивка MARLIN3_19B_W21.05.3) |
| Точка на 5 ГГц, канал 36, VHT80 | **Работает, по умолчанию с r17.** 1 ч 14 мин, два клиента на VHT-MCS 9 / 433 Мбит/с, без падений прошивки |
| Точка на 2,4 ГГц, HT20 | Работает (телефон выходит в интернет через плату) |
| Клиент (STA) | **Работает на 2,4 ГГц** (хотспот телефона): подключение, DHCP, интернет, переподключение после возврата аплинка (~35 с), сигнал и скорость показываются |
| Точка и клиент одновременно (репитер) | **Экспериментально, с beta 2.** Разные MAC, клиенты LAN выходят в интернет через аплинк. Перезапуск Wi-Fi может повесить плату (см. описание beta 2); канал точки ставьте равным каналу аплинка |
| LTE-модем как аплинк, Wi-Fi для клиентов | Работает (QMI-модем, ModemManager). Образ кладёт `modem` и `wwan` в зону wan |
| Список клиентов, байты и пакеты по клиентам | Работает (патч 270). TX — то, что отдано в прошивку |
| TX-скорость по клиентам | Работает с `cp_txrate=1` (патч 240): живая скорость, например 433,3 Мбит/с VHT-MCS 9 80 МГц, меняется с условиями. По умолчанию выключено |
| RSSI и RX-скорость клиентов (режим точки) | Недоступно: прошивка их не отдаёт (RE §37–§43, §52, §58). LuCI показывает точку как работающую с числом клиентов, а сигнал клиента — как `---` с подсказкой, почему (`opiz3-luci-nosig`) |
| Мощность передатчика | Не показывается: в прошивке нет команды её прочитать (RE §59) |
| Журнал `wifi up` | Чистый: без `-95`/`-12`, настоящий MAC радио (патч 280) |
| Имя драйвера | «Unisoc UWE5622» в LuCI и в `iwinfo` |
| Восстановление прошивки | Работает: `uwe5622-recover` возвращает Wi-Fi за ~14 с (сброс SDIO-хоста; RE §61) |
| Ширина канала из LuCI | Ограничивается допустимой для драйвера при каждом «Сохранить и применить» (r17) |
| Сканирование при работающей точке | Работает, клиенты не отваливаются |
| Панель платы, страница частоты процессора | Работают (`luci-app-opiz3-status`) |
| Каналы DFS (52–144), 160 МГц, 40 МГц на 2,4 ГГц | Закрыты (не проверены; непроверенные настройки роняли прошивку, RE §45) |
| Загрузка драйвера при старте | Отложенная, после поднятия сети, чтобы зависший опрос SDIO не мешал Ethernet ([планы](#над-чем-работаем), п. 4) |
| Orange Pi Zero 2 | Собран, не проверен |
| Orange Pi Zero 2W | Загружается, точка работает (1 ГБ, отчёт пользователя; с beta 2) |
| Ethernet после `reboot` (Zero 3) | Работает с beta 2 (U-Boot снова сбрасывает PHY; `opiz3-emac` — запасной путь) |
| USB2/USB3 на 13-контактной гребёнке / плате расширения Zero 2W | Включены с beta 2; контроллеры поднимаются, устройство на гребёнке пока не проверено |

Параметры модуля в `/etc/uwe5622.options`:

```
max_bw_2g=20      # 20 или 40 (40 не проверено)
max_bw_5g=80      # 20, 40 или 80 (80 по умолчанию с r17)
allow_dfs=0
cp_txrate=0       # 1: TX-скорость клиентов из прошивки
```

Драйвер объявляет только эти ширины и каналы, а `uwe5622-clamp-htmode`
понижает `htmode` в настройках беспроводной сети до допустимого — при
загрузке и после каждого изменения настроек. Без этого неподходящая для
прошивки настройка либо не даёт запуститься hostapd, либо роняет прошивку.

## Платы

| Плата | SoC | Образ | Состояние |
|---|---|---|---|
| Orange Pi Zero 3 | H618 | `xunlong_orangepi-zero3` | **Проверена** на железе |
| Orange Pi Zero 2 | H616 | `xunlong_orangepi-zero2` | **Собрана, не проверена — нужны тестеры.** Тот же модуль Wi-Fi и та же разводка, что у Zero 3 (общий `sun50i-h616-orangepi-zero.dtsi`, сброс на PG18); изменение DTB такое же, как в патче ядра 900 |
| Orange Pi Zero 2W | H618 | `xunlong_orangepi-zero2w` | **Загружается, Wi-Fi работает** (плата на 1 ГБ, тестовый образ 2026-10-07: SDIO-карта найдена, прошивка MARLIN3_19B_W21.05.3 загружена, точка на 5 ГГц VHT80, клиент подключился; с beta 2). В device tree производителя те же узлы Wi-Fi, что у его Zero 3 (`mmc1`, сброс PG18, часы RTC 32 кГц), и производитель грузит тот же драйвер UWE5622. Ethernet нет: используйте точку `OPiZ2W` первой загрузки |

**Платы на 1,5 ГБ** (Zero 3, Zero 2W): U-Boot 2025.01 из OpenWrt 25.12.5
понимает только объёмы памяти, равные степени двойки, и такие платы не
загружает. С beta 2 в образах Zero 3 и Zero 2W стоит U-Boot 2026.04
(собирается в CI с TF-A 2.10), который видит 1,5 и 3 ГБ. Beta 1 на платах
с 1,5 ГБ не загружается.

Другие платы с модулем AW859A / UWE5622 (по спецификациям производителей,
здесь не проверялись):

- **Orange Pi 3 LTS** (H6): для неё был написан исходный пакет OpenWrt;
  отдельного профиля 3 LTS в OpenWrt нет.
- Другие платы и ТВ-приставки с этим модулем.

Что подойдёт для любой из них:

- патчи драйвера (010–330) и пакеты apk-репозитория, собранные для
  `sunxi/cortexa53` (H6, H616, H618);
- разбор прошивки в [docs/](docs/): `wcnmodem.bin` — тот же файл;
- патч 250 (перерегистрация SDIO-драйвера) — на любой плате Allwinner.

Что нужно для каждой платы: узлы Wi-Fi в device tree (SDIO-контроллер,
питание, GPIO сброса), профиль образа в CI и проверка на железе. Отчёты с
выводом `scripts/collect-debug.sh` приветствуются.

## Производительность

Замеры на Zero 3, 5 ГГц, канал 36, одна антенна, Android-телефон примерно в
1 м, старый образ (патчи до 230):

| Тест | Результат |
|---|---|
| iperf3 телефон → плата, 5 потоков | 160 Мбит/с (выше потолка VHT20 ~87 Мбит/с: канал действительно 80 МГц) |
| Канальная скорость телефона (его статистика) | RX 390 / TX 433 Мбит/с (VHT80 MCS8/9, SGI) |
| Rate control при −69 дБм (`cp_sta_table`) | VHT80 MCS2 |
| Клиент 1 iperf3 без ограничения + клиент 2 speedtest | у клиента 2 ≤ 5 Мбит/с |
| Клиент 1 iperf3 с ограничением 50 Мбит/с + клиент 2 speedtest | у клиента 2 76 вниз / 31 вверх (потолок интернета ~100) |
| Процессор под нагрузкой | 85–95 % простоя, ни одно ядро не загружено полностью |

Вывод: общий потолок около 160 Мбит/с, и неограниченная TCP-отдача одного
клиента забирает почти всё; ниже насыщения клиенты делят канал честно.
Процессор свободен, поток приёма SDIO ждёт ввода-вывода, а шина SDIO
работает в режиме High Speed (50 МГц, 4 бита, ~200 Мбит/с сырой скорости),
что и даёт этот потолок. Следующий опыт — SDIO UHS SDR50 (100 МГц) в device
tree.

## Скачать

Каждая сборка даёт:

- **Образ** (`opiz3-image-25.12.5`): образы для SD-карты в вариантах
  squashfs и ext4. Записываются как любой образ OpenWrt для sunxi.
  С r18 плата при первой загрузке сама поднимает точку доступа: имя по
  плате — **`OPiZ3`**, **`OPiZ2W`** или **`OPiZ2`**, 5 ГГц, канал 36
  (VHT80), WPA2, пароль **`12345678test`**. LuCI доступен по
  http://192.168.1.1 через Wi-Fi, без кабеля.

  > ⚠️ **Пароль Wi-Fi по умолчанию публичный — смените его сразу** после
  > первого входа (LuCI → Network → Wireless → Edit → Wireless Security) и
  > задайте пароль root (System → Administration). Пока пароль не сменён,
  > на главной странице LuCI (блок «Board») висит предупреждение.

- **ImageBuilder** (`opiz3-imagebuilder-25.12.5`): официальный ImageBuilder,
  в ядро которого уже добавлен Wi-Fi в device tree, с нашими пакетами,
  ключом и репозиторием. Свой набор пакетов:
  ```
  make image PROFILE=xunlong_orangepi-zero3 PACKAGES="... kmod-uwe5622 uwe5622-firmware ..."
  ```
- **apk-репозиторий** на GitHub Pages:
  `https://<owner>.github.io/opiz3-wlan-backport/25.12.5/sunxi-cortexa53/packages.adb`.
  Образ уже содержит его ключ и адрес, так что `apk update` и `apk add`
  работают и для официальных репозиториев, и для нашего.

Релизы: фиксированные, например
[`opiz3-25.12.5-beta2`](../../releases/tag/opiz3-25.12.5-beta2), и
«скользящий» `opiz3-25.12.5-latest`, собираемый из `main`. Обновление платы
по сети (`-p` записывает и U-Boot; вид образа, squashfs или ext4, оставляйте
прежним):

```sh
wget -O /tmp/fw.img.gz https://github.com/Medvedolog/opiz3-wlan-backport/releases/download/opiz3-25.12.5-beta2/openwrt-25.12.5-sunxi-cortexa53-xunlong_orangepi-zero3-squashfs-sdcard.img.gz
sysupgrade -p /tmp/fw.img.gz
```

Подробности и что делает `-n` — в
[описании beta 2](docs/releases/opiz3-25.12.5-beta2.md).

В образе по умолчанию:

- LuCI с темой Footstrap (палитра проекта; фон с лапами есть, но выключен:
  `opiz3-pattern paws`). Другие цвета: меню Footstrap Appearance → Palette
  (Footstrap, Bootstrap, высокий контраст…) и поля цветов; выбор хранится в
  браузере и перекрывает настройки роутера;
- AmneziaWG и WireGuard;
- sing-box;
- драйверы USB-свистков Wi-Fi;
- поддержка модемов (ModemManager, QMI с `qmicli`, MBIM, NCM, RNDIS,
  последовательные порты).

> **Страница AmneziaWG исправлена после beta 2.** В образе beta 2 стояла
> старая страница для AWG 1.0: при импорте `.conf` терялись Jc/S/H, а
> полей для параметров AWG 2.0 (S3/S4, I1–I5, диапазоны H1–H4,
> ContentPaddingAddition, Rekey…) не было, хотя модуль ядра их
> поддерживал. В репозитории теперь актуальная страница
> (`luci-proto-amneziawg` 3.1, ставится под старым именем
> `luci-app-amneziawg`). Обновление на плате, без перепрошивки, настройки
> сохраняются:
> ```sh
> apk update && apk upgrade luci-app-amneziawg
> ```
> затем обновите LuCI через Ctrl+F5 и импортируйте `.conf` заново.

Полный список с причиной для каждого пакета — в
[docs/IMAGE-PACKAGES.md](docs/IMAGE-PACKAGES.md). Всё остальное ставится
через `apk`.

## Предыстория: Wi-Fi-чип от ТВ-приставки

Единственная публичная прошивка модуля, `wcnmodem.bin`
`MARLIN3_19B_W21.05.3` (2021-12-15), называет свой проект
`sc2355_marlin3_lite_ott`: Marlin3 Lite — это чип (UWE5622, «M3L» в BSP
производителя), OTT — линейка ТВ-приставок. Драйвер производителя тоже
собирается с `-DOTT_UWE`. Модуль делался прежде всего как Wi-Fi-клиент в
приставке, и режим точки доступа в прошивке минимальный: канал точки
берётся из IE маяка (§44), неподдерживаемый канал роняет прошивку вместо
ошибки команды (§45), сигнал и скорость клиентов в режиме точки не
отдаются (§37–§43), а маяк собирается в ПЗУ (§64). Это наш вывод из
разбора, а не заявление производителя; он объясняет, почему большая часть
проекта — обходы ограничений прошивки. См.
[§65](docs/WCNMODEM-REVERSE-ENGINEERING.md).

## Предыстория: прежние попытки

Запустить этот Wi-Fi на OpenWrt пытаются уже несколько лет. Проект опирается
на эти работы.

- **Основной OpenWrt.**
  [openwrt/openwrt#18494](https://github.com/openwrt/openwrt/issues/18494)
  («Wi-Fi (AW859A) not detected on Orange Pi Zero 3», 24.10.0) закрыт как
  *not planned*. Единственный доступный драйвер — большой внешний драйвер
  производителя, а такое в OpenWrt не принимают. Поэтому в официальных
  образах Wi-Fi этой платы не поддерживается.
- **[armbian/uwe5622](https://github.com/armbian/uwe5622).** Поддерживаемый
  драйвер производителя (транспорт UNISOC WCN + cfg80211-драйвер
  `sprdwl_ng`) для ядер Armbian. Наша основа, зафиксирована на `cc2835a`.
- **[DeepAQ/openwrt-uwe5622-sunxi](https://github.com/DeepAQ/openwrt-uwe5622-sunxi).**
  Ранняя интеграция в OpenWrt. Несёт более старый драйвер патчем на ~13 МБ
  внутри пакета `mac80211`. Её ключевое исправление — IE DS Parameter Set в
  маяках 5 ГГц — вообще делает точку на 5 ГГц рабочей. У нас это патч 180,
  а §44 разбора прошивки объясняет, зачем он нужен.
- **[rizkirmdhnnn/openwrt-orangepi-zero3-wifi](https://github.com/rizkirmdhnnn/openwrt-orangepi-zero3-wifi).**
  Пакетирование для OpenWrt, которое служило контрольной точкой на старте
  порта.
- **[Anieake/openwrt-orangepi-zero2-zero3-wifi-modem](https://github.com/Anieake/openwrt-orangepi-zero2-zero3-wifi-modem)**
  (сборка с форума 4PDA). Полный образ на OpenWrt 25.12.0 с Wi-Fi на основе
  DeepAQ, поддержкой модемов и Bluetooth. В его README Zero 2 указан как
  рабочий, а Zero 3 — как требующий проверки. У него своё ядро и замена
  `mac80211`, поэтому официальные kmod не ставятся, а для сборки нужны
  ручные правки `-Werror` в `build_dir`.

Все они поднимают радио. Ни одна не меняла драйвер дальше сборки. Падения,
зависания, бессмысленная статистика клиентов и поведение прошивки
оставались как были.

## Что добавляет этот проект

| | Драйвер производителя / прежние сборки | Этот проект |
|---|---|---|
| OpenWrt | 24.10 / 25.12.0, своё ядро | 25.12.5, **официальное ядро** |
| Официальные kmod через `apk` | Нет (другой ABI ядра) | **Да** |
| Основа драйвера | Старые исходники производителя | Актуальный Armbian `cc2835a` + 30 патчей |
| Точка на 5 ГГц | Через исправление DeepAQ (DS IE) | То же исправление, причина найдена в прошивке |
| Безопасность памяти | Код производителя как есть | Исправлено: переполнение массива ADDBA (190), спящее выделение памяти в атомарном контексте (130), гонка ADDBA/очереди (160), утечка ссылки на карту (220), VLA на стеке (070) |
| Список клиентов в LuCI | В драйвере производителя нет `dump_station` | Реализован (060) |
| Статистика клиентов | Драйвер производителя отдаёт для каждого клиента значения самого радио | Только реально измеренное: счётчики хоста по клиентам (150); без поддельных RSSI и скорости (120, 140) |
| Настройки, роняющие прошивку | Принимаются | Блокируются в cfg80211 (200) |
| Падение прошивки | Драйвер не восстанавливается: Wi-Fi мёртв до перезагрузки | Автоматическая перезагрузка драйвера с ограничением частоты (`uwe5622-recover`) |
| Имя в LuCI | «Generic» | «Unisoc UWE5622» (патч iwinfo; также в `iwinfo`) |
| Состояние платы | Нет | Панель на LuCI Overview: температуры SoC, частота процессора, состояние драйвера и прошивки Wi-Fi, ширина канала у хоста и в прошивке, частота шины SDIO, восстановления прошивки (`luci-app-opiz3-status`) |
| Частота процессора | По умолчанию в ядре «performance» (всегда максимальная частота, 1416 или 1512 МГц в зависимости от бина чипа) | `ondemand` по умолчанию; регулятор и мин./макс. — в LuCI System → CPU frequency (`/etc/config/opiz3`). Без разгона: таблица заканчивается на 1512 МГц / 1,10 В SoC (1416 МГц на части чипов, по бину из eFuse), а Wi-Fi упирается в SDIO, а не в процессор |
| Устройство прошивки | Неизвестно | Разобрано, опубликовано ([заметки](docs/WCNMODEM-REVERSE-ENGINEERING.md)) |
| Сборка | Ручные шаги | CI: SDK + ImageBuilder, подписанный репозиторий, проверки образа |

Разбор прошивки объясняет три давние проблемы:

1. **Зачем 5 ГГц понадобилось исправление DeepAQ.** Прошивка берёт канал
   точки из IE DS Parameter Set в маяке, а hostapd в маяки 5 ГГц этот IE не
   кладёт (§44).
2. **Почему некоторые настройки канала убивают Wi-Fi до перезагрузки.** RF-код
   падает, вместо того чтобы отклонить канал, на который не может
   настроиться, а драйвер производителя не восстанавливается (§45). Патч 200
   и `uwe5622-recover` закрывают обе половины.
3. **Почему LuCI не показывает сигнал и скорость клиентов.** В режиме точки
   их не отдаёт ни одна команда или событие (§37–§43, §52). Прошивка их
   ведёт в таблице rate control по станциям, и индекс таблицы совпадает с
   аппаратной таблицей станций LUT (§46–§49). Патч 230 читает эту таблицу
   через SDIO для диагностики.

## Над чем работаем

После beta 2 (по порядку): повторный стресс-тест репитера на чистом образе;
код страны для прошивки (правила из регуляторной базы ядра);
восстановление Wi-Fi, которое не ждёт мёртвую прошивку, держа сетевую
блокировку; отправка исправления PHY YT8531 в U-Boot
([черновик](docs/upstream/uboot-yt8531-power-down.md)) и предложение
U-Boot 2026.04 в OpenWrt ([текст PR и инструкция](docs/upstream/openwrt-uboot-sunxi-pr.ru.md)).
Дальше:

1. **Проверка последней серии на железе.**
   - Патчи 240–280 (`cp_txrate=1` против того, что показывает телефон).
   - Восстановление после падения (перезагрузка драйвера, затем сброс
     SDIO-хоста).
   - Ограничение каналов.
   - VHT80 под тяжёлой длительной нагрузкой (iperf3 12+ часов); час
     умеренной нагрузки пройден.
2. **RSSI и скорость по клиентам.**
   - TX-скорость: сверить `cp_txrate=1` со скоростью телефона и включить по
     умолчанию.
   - RSSI: сравнить память прошивки близко/далеко/близко
     (`scripts/cp-mem-diff.sh`).
3. **Энергосбережение.** Найти, какой переход (PS прошивки, сон WCN,
   пробуждение SDIO) теряет мультикаст или зависает, прежде чем включать
   его снова.
4. **Обычная загрузка драйвера при старте.** Найти, почему опрос SDIO может
   зависнуть при загрузке, чтобы убрать отложенный запуск.
5. **Новый драйвер.**
   - Стек производителя — около 76 тыс. строк.
   - Планируется cfg80211-драйвер точки и клиента под эту прошивку на
     7–8 тыс. строк, с проверкой всего до отправки в прошивку и
     восстановлением после падения внутри ядра.
   - Архитектура и карта протокола:
     [docs/NEW-DRIVER-ARCHITECTURE.md](docs/NEW-DRIVER-ARCHITECTURE.md).
   - Это и единственный реальный путь в основное ядро.

Другие части:

- **Патч U-Boot** ([`uboot/patches/`](uboot/patches/)): снова мягко
  сбрасывает PHY Ethernet при старте, как U-Boot делал до 2025.01; без него
  порт после горячей перезагрузки не работает.
- **USB2/USB3:** образ включает `ehci2/ohci2/ehci3/ohci3` в DTB рядом с
  узлами Wi-Fi.
- **Патч ядра 900:**
  [`target/linux/sunxi/patches-6.12/`](target/linux/sunxi/patches-6.12/)
  добавляет узлы Wi-Fi в device tree Zero 2 / Zero 3.
  [`scripts/zero3-dtb-add-wifi.py`](scripts/zero3-dtb-add-wifi.py) делает
  то же с официальным DTB.
- **Патч iwinfo 900:** опознаёт платформенные Wi-Fi-устройства по modalias.
  Утилита `iwinfo` в 25.12 — скрипт на ucode со своей таблицей устройств;
  `uwe5622-iwinfo-name` (запускается при загрузке) добавляет туда тот же
  запасной путь по modalias.
- **`luci-app-opiz3-status`:** панель «Board» на Status → Overview. Данные
  даёт плагин rpcd на ucode (`ubus call luci.opiz3 status`), который только
  читает sysfs/debugfs и никогда не обращается к чипу. Мощность передатчика
  числом нигде не показывается: прошивка берёт её из своего ini-файла, и
  команды прочитать её нет, поэтому LuCI лучше не показывает ничего, чем
  выдуманное значение.

## Сборка

Workflow в `.github/workflows/`:

- **`build-ib.yml` (основной).** Пакеты — официальным SDK, образ —
  официальным ImageBuilder. Он:
  - добавляет DTB с Wi-Fi в готовое FIT-ядро;
  - проверяет образ (пакеты, DTB внутри FIT, файлы rootfs, iwinfo);
  - публикует подписанный репозиторий в `gh-pages` и «скользящий» релиз.

  Пакеты пересобираются, только когда меняется `package/` или задача
  сборки пакетов. Иначе берётся последний подписанный репозиторий, и сборка
  занимает несколько минут. Пересборка начинается с кешированного
  `build_dir` SDK. Параметры ручного запуска: `rebuild_packages`,
  `clean_sdk` и `runner` (`github` или свой `self-hosted` раннер для сборки
  пакетов и образа).
- **`release-tag.yml`.** Превращает проверенную «скользящую» сборку в
  фиксированный релиз с описанием из `docs/releases/<тег>.md`; ничего не
  пересобирается.
- **`build-image.yml`.** Полная сборка из исходников с патчем ядра 900, для
  разработки. Ядро у неё не официальное, поэтому официальные kmod на неё не
  ставятся.

Однократная настройка публикации:

1. Создать ключ подписи:
   `openssl ecparam -name prime256v1 -genkey -noout -out opiz3-wlan.key`.
2. Положить его содержимое в секрет `APK_SIGN_KEY` (Settings → Secrets →
   Actions).
3. Settings → Pages → Deploy from branch `gh-pages`. Ветка появится после
   первой публикующей сборки.

## Диагностика

На плате:

```sh
dmesg | grep -e sprdwl -e 'channel limits'
cat /sys/module/sprdwl_ng/parameters/max_bw_5g
iw dev; iw dev wlan0 station dump
logread -e uwe5622-recover
cat /sys/kernel/debug/sprdwl_debug/peer_stats     # счётчики хоста по клиентам
cat /sys/kernel/debug/sprdwl_debug/cp_sta_table   # таблица скорости/RSSI в прошивке
```

`scripts/collect-debug.sh` на плате собирает полный диагностический архив в
`/tmp` (пароли и ключи скрыты):

```sh
wget -O /tmp/collect-debug.sh https://raw.githubusercontent.com/Medvedolog/opiz3-wlan-backport/main/scripts/collect-debug.sh
sh /tmp/collect-debug.sh
```

Заберите архив через `scp -O` и приложите к отчёту.
